❯ As I can see, here the project works like it reads from the .md file. My      
  question is how? Answer in 3 lines.                                           

● Jekyll scans folders like _pages/, _posts/, _projects/, and _bibliography/,
  reading each .md file's YAML front matter (the --- block: layout, title,
  permalink, etc.) plus its Markdown/HTML body. It wraps the body in the
  matching gem-owned layout (layout: page/about), runs any Liquid tags ({% for 
  %}, {% bibliography %}), converts Markdown to HTML, and writes the result to
  _site/ as static pages. The dev server rebuilds and serves that _site/ on
  every save — which is why editing a .md file instantly updates the page.

❯ Why can't we directly use html and css ? Answer in 3 lines.                   

● You actually can — and we already do: the <style> blocks and raw HTML inside
  the .md files are just plain HTML/CSS. What the .md + Jekyll wrapper buys you
  is not having to hand-copy the shared navbar, footer, <head>/SEO, and theme
  toggle into every single page — the layout injects them once, so each file
  only holds its own content. Going pure static HTML/CSS is entirely possible
  (that's basically what the Astro migration becomes), but you'd either repeat
  that shared chrome on every page or reintroduce a templating layer to avoid
  it.

❯ Why can't we use next.js It is more modern and better and has more            
  expression?                                                                   
  Answer in 3 lines.                                                            

● We can — Next.js would work fine. But for a portfolio that's almost entirely
  static text, Next.js ships a React runtime and hydration you don't need,
  whereas Astro renders to plain HTML with zero JS by default — which directly
  serves the thing that drove the whole stack decision: being readable by Google
  Scholar, link-preview crawlers, and LLMs that don't run JavaScript. Astro
  still lets you drop in React (or any framework) components exactly where you
  want interactivity, so you keep Next's expressiveness without paying its
  weight on every page. Next.js shines for apps with dynamic data, auth, and
  server logic — none of which a CV-style site has.
